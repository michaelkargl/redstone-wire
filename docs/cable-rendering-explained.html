RedstoneWire · Minecraft 26.2 · rendering

Why the Cables Vanish

Your mod strings redstone cables between blocks. Walk around and they blink out for no obvious reason. The cause is one invisible crate that nobody ever resized — and once you can see the crate, the behaviour stops being random.

01 / THE SETUP

A cable is not a block

Minecraft is very good at drawing blocks. It bakes a whole chunk of them into one big pre-built mesh and throws it at the graphics card in a single go. Fast, and nothing you need to think about.

But a cable stretching from one block to another doesn't fit in any single block's square. So it can't be baked. Instead your mod registers a block entity renderer — a small piece of code attached to a block that says "every frame, give me a moment and I'll draw something extra." Three of them, in fact: RedstoneConnectorBlockEntityRenderer, and the input and output equivalents.

That per-frame budget is precious, so Minecraft is aggressive about skipping renderers it believes you can't see. Which brings us to the crate.

02 / THE CONCEPT

Every object gets an invisible crate

Working out whether a complicated shape is on screen is expensive. So the game doesn't. Instead, every drawable object declares a simple rectangular box — a crate — that is supposed to contain everything it draws. The proper name is an axis-aligned bounding box; in the code it's AABB.

Then the game asks one cheap question per object: is any corner of that crate inside what the camera can see? No → skip the object entirely, don't even call its draw code. This is called culling, and it is why Minecraft runs at all.

The rule that got broken

The crate must be at least as big as what you actually draw. Draw outside your crate and the game will happily throw you away while your geometry was still on screen. It has no way to know it was wrong.

03 / SEE IT HAPPEN

The camera's cone

What the camera can see is a pyramid spreading out from your eyes. The jargon word is frustum. You don't need the word — just picture a cone of vision.

Below is a map view, looking straight down. Turn your head with the slider. The blue wedge is what's on screen; the dashed box is the crate the cable's renderer declares. The cable is drawn only when the crate and the wedge overlap.

FRUSTUM CULL · TOP-DOWN VIEW drag the slider to look around

With the toggle off, swing the view so the blue input block slips past the edge of the wedge. The cable disappears all at once — including the stretch of it that is still plainly inside the wedge. That is the bug, exactly as you saw it in game.

Turn the toggle on and swing again. Now the crate covers the whole cable, so the cable survives until the last of it genuinely leaves the view.

Why it felt like it had no pattern

A cable between blocks A and B is drawn by only one of them — whichever position sorts lower (blockPos.compareTo(connection) < 0 in the connector renderer). So each cable's fate is tied to one specific end, and which end is essentially arbitrary from where you're standing. One cable dies when you turn left, the next when you turn right.

04 / THE FULL CIRCUIT

Three gates, wired in series

The crate is one of three checks a cable has to pass before a single triangle reaches your screen. Like redstone torches in a line: all three have to be lit.

1 · Is the block's chunk on screen at all?

Minecraft culls whole 16×16×16 chunk sections first. If the cable's anchor block sits in a section that's off screen or fully hidden behind terrain, nothing downstream runs. Rare for cables strung overhead — and not something a bounding box can fix.

LevelRenderer#extractVisibleBlockEntities → this.visibleSections

2 · Does the crate overlap the view cone?

This was the bug. Nothing overrode the crate, so NeoForge handed the game its default: new AABB(blockEntity.getBlockPos()) — a single 1×1×1 cube. Cables 30 blocks long, judged by a one-block crate.

BlockEntityRenderDispatcher:97 → frustum.isVisible(getRenderBoundingBox(..))

3 · Is the camera within 64 blocks?

A second, quieter cut. getViewDistance() defaults to 64, so cables stopped drawing well before their blocks did. Raised to 256 — a render distance of 16 chunks.

BlockEntityRenderer#shouldRender → closerThan(cameraPos, getViewDistance())

05 / THE FIX

Tell the truth about the crate

One shared helper in CableRenderer, and three small overrides — one per renderer. Start from the block's own cube, stretch it to swallow every connected block, then drop the floor by the sag cap.

1 Start with the block's own cube
new AABB(entity.getBlockPos())

One 1×1×1 cube. This is the default the game hands you, and where the vanishing came from.

2 Stretch it over every connection
bounds = bounds.minmax(new AABB(c))

Once per connection. minmax returns the smallest crate holding both.

3 Drop the floor for the sag
bounds.expandTowards(0, -maxSag, 0)

Negative Y is down. Now nothing the renderer draws lives outside the crate.

BEFORE · INHERITED DEFAULT 
// nothing overridden, so NeoForge
// supplied this for every renderer:

default AABB getRenderBoundingBox(T be) {
    return new AABB(be.getBlockPos());
}
//                    ^^^^^^^^^^^^^
//         one 1x1x1 cube. that's it.

default int getViewDistance() {
    return 64;
}
AFTER · CableRenderer.cableBounds() 
public static AABB cableBounds(
        RedstoneWireBlockEntity entity) {

    var bounds = new AABB(entity.getBlockPos());

    // swallow every connected block
    for (BlockPos c : entity.getConnections()) {
        bounds = bounds.minmax(new AABB(c));
    }

    // drop the floor for the sag
    return bounds.expandTowards(
            0, -maxSagAmountInBlocks, 0);
}
  • new AABB(blockPos) — the 1×1×1 cube sitting at that block.
  • minmax(other) — the smallest crate containing both crates. Call it once per connection and the crate grows to cover the lot.
  • expandTowards(0, -1, 0) — push the bottom face down one block. Negative Y is down in Minecraft.

Deliberately too big

A cable only sags the full block if it's long; shorter ones droop less. The crate uses the cap for all of them. Over-sized is the safe direction to be wrong in — you waste a few cheap overlap tests. Under-sized is the bug you just spent an evening chasing.

06 / STILL OPEN

One thing this doesn't fix

While reading the three renderers, a second bug turned up. The connector guards against drawing a cable from both ends with that compareTo check. The input and output renderers have no such guard — they draw every connection unconditionally.

So an input-to-connector cable gets drawn twice: once by the input, and again by the connector whenever the connector's position happens to sort lower. You'd see it as slightly darker cables and a faint shimmer where the two copies fight over the same pixels.

That's a separate defect from the vanishing, so it's filed separately as RW-12 rather than smuggled into this fix.
