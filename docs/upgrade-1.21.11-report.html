Build-tool tour

What ModDevGradle actually is

ModDevGradle is NeoForge's development plugin for Gradle. It turns an ordinary Java/Gradle project into a Minecraft mod development workspace: it prepares the Minecraft and NeoForge dependencies, gives Gradle the mod-specific build rules, creates runnable game configurations, and packages the finished mod.

C# lens: think of Gradle as a mixture of the .NET CLI, MSBuild, and NuGet. build.gradle is roughly your .csproj plus custom build targets. ModDevGradle is the plugin that adds the Minecraft/NeoForge-specific targets and project model.
gradle.propertiesdeclares Minecraft, NeoForge, mappings, and mod versions
build.gradleapplies ModDevGradle and describes runs, sources, and build rules
Dev workspacedownloads and prepares Minecraft + NeoForge artifacts with mappings and browsable sources
IDE + Gradle taskscompile, launch client/server, run GameTests, and generate data
Mod JARbuild/libs/redstone_wire-1.0.9.jar

The one line that switches it on

plugins { id 'net.neoforged.moddev' version '2.0.144' }

net.neoforged.moddev identifies the plugin. 2.0.144 is the build plugin's version—not the Minecraft version, NeoForge version, Java version, or your mod's release version.

Applying it adds the neoForge { ... } configuration language used later in build.gradle. Without that plugin, plain Gradle would not understand settings such as version, parchment, runs, client(), server(), or ideSyncTask in that block.

It is not

Part of the mod players install

ModDevGradle is development/build tooling. It does not run inside a player's Minecraft instance and it is not a substitute for the NeoForge loader.

It is

The workshop around the mod

It prepares the workbench, tools, test launches, and packaging process that let your source code become a NeoForge-compatible JAR.

Why it changed from 2.0.139 to 2.0.144: this upgrades the build integration used by the 1.21.11 project setup. It does not change the game to Minecraft 2.0.144. Minecraft remains 1.21.11, NeoForge remains 21.11.45, and the mod is released as 1.0.9.
When to reload Gradle: after changing build.gradle or gradle.properties, use IntelliJ's Reload All Gradle Projects. That makes the editor, compiler classpath, and generated run configurations agree with the new build model. The official ModDevGradle project documents the plugin itself, while the NeoForge getting-started guide explains project import and Gradle builds.
Making Minecraft source readable

What Parchment is

Parchment is a community-maintained, mod-loader-neutral data set of Minecraft parameter names and Javadocs. ModDevGradle layers that information over Mojang's official mappings so IntelliJ can show more meaningful method parameters and explanations while you work.

First, “mapping” in plain English: released Minecraft is compiled Java bytecode, and production symbols are not designed to be pleasant source code. A mapping is translation metadata that helps development tools present those symbols meaningfully. Mojang's official mappings provide the main class, field, and method names; Parchment augments them with parameter names and documentation.
C# lens: imagine referencing a DLL where IntelliSense could only show void Update(BlockState p0, Level p1, BlockPos p2). Parchment is like applying an external metadata/XML-documentation package that lets the IDE show meaningful names such as state, level, and pos, plus useful API comments. It improves the development view; it does not replace the DLL.
Minecraft bytecodethe compiled game that tools start from
Mojang mappingsofficial class, method, and field names
Parchment overlaycommunity parameter names + Javadocs
ModDevGradleapplies the selected mapping layers to the dev workspace
IntelliJshows more readable signatures, hints, and documentation

A small illustrative example

With only incomplete parameter information:

void update( BlockState p0, Level p1, BlockPos p2 )

After the Parchment overlay:

/** * Updates the block at the supplied position. */ void update( BlockState state, Level level, BlockPos pos )

This is a teaching example, not a literal Minecraft method. The important difference is the developer-facing names and documentation.

How this project selects it

neoForge { parchment { minecraftVersion = project.parchment_minecraft_version mappingsVersion = project.parchment_mappings_version } } # gradle.properties parchment_minecraft_version=1.21.11 parchment_mappings_version=2025.12.20

parchment_minecraft_version says which Minecraft code the data describes. parchment_mappings_version selects a particular published Parchment data release; its value is date-based.

Here both the mod and the mapping data target Minecraft 1.21.11, while 2025.12.20 identifies the chosen Parchment release—not another Minecraft version.

Parchment doesParchment does not
Improve parameter names shown in decompiled Minecraft source.Add new methods, blocks, hooks, or gameplay behavior.
Attach community-written Javadocs that explain parts of the API.Replace NeoForge, ModDevGradle, or Mojang's official mappings.
Help humans understand arguments while reading and calling methods.Become a library that players must install with the mod.
Make API changes easier to reason about during an upgrade.Change Java method identity: parameter types and order still define the callable signature.
Important: Parchment can make an API easier to understand, but it cannot make old code compatible with a changed Minecraft API. If a method was removed or its parameter types changed in 1.21.11, the Java code still needs a real migration.
Why we use it here: readable names such as state, level, and pos make compiler errors and decompiled Minecraft source much easier to follow while learning the API. See the official Parchment repository and its version and setup guide.
Before the details

A Minecraft modding mental model

These five concepts explain most of the project. The names are Minecraft-specific, but the separation is familiar from application and game architecture.

B

Block

A singleton type definition: rules, shape, interaction methods. Roughly a registered service/type, not one placed instance.

S

BlockState

An immutable value describing a placed block variant, such as facing north or power level 7.

BE

BlockEntity

Mutable data attached to a world position. Here it stores cable connections and synchronizes them.

R

Renderer

Client-only code that converts a safe snapshot of game state into geometry submitted to the GPU.

{ }

Resources

JSON/NBT data for models, item definitions, recipes, translations, metadata, and GameTest instances.

Important: changing a Block API can break startup, changing a BlockEntity API can break saved worlds, changing a renderer can break only the client, and changing JSON can fail during resource loading. That is why the validation used several layers.
How the migration was proven

The failure → evidence → fix timeline

A successful compile is necessary, but it is not proof that a Minecraft mod can start. Each validation layer found a different class of problem.

1 · Compiler/API migration

Updated changed method signatures, storage interfaces, render interfaces, registries, and resource formats until a full IntelliJ rebuild succeeded.

2 · Real server startup found “Block id not set”

The old generic registration constructed blocks before 1.21.11 had assigned their IDs. The stack trace led directly to ModBlocks.

3 · ID-aware registration fixed startup

DeferredRegister.Blocks.registerBlock applies Properties.setId(...) before calling each constructor. The mod then loaded on Minecraft 1.21.11 and NeoForge 21.11.45.

4 · GameTests exposed the coordinate-system change

Test fixtures loaded, but coordinates still included the old controller-block offset. Runtime evidence and the NBT templates showed every relevant Y coordinate was one too high.

5 · All behavior and removal tests passed

After correcting the fixture coordinates and adding the connected-block removal regression, the final server run completed this mod’s four tests successfully. (The runner prints “5 required tests”: Minecraft ships one test instance of its own, minecraft:always_pass, and it is counted too. Removing one mod instance drops the count to four, which is how that was confirmed.)

6 · Client pipeline probe fired

An IntelliJ non-suspending runtime probe at pipeline registration observed redstone_wire:pipeline/cable, with no client error markers and a normal shutdown.

7 · Distribution build completed

Gradle’s full build lifecycle completed and produced the 1.0.9 JAR.

Migration deep dives

This section follows the actual 1.21.11 code path. Each explanation starts with the runtime behavior, then translates the Java or Minecraft terminology into a C#-friendly mental model.

Tip: wide comparison tables scroll sideways on a narrow screen.

1 · The renderer no longer draws directly from the block entity

In 1.21.1 Minecraft called one method that both read the live block entity and immediately wrote vertices. In 1.21.11 those responsibilities are deliberately split into extraction and submission.

1.21.1 render(entity, partialTicks, PoseStack, MultiBufferSource, light, overlay) read mutable entity and emit vertices now
→
1.21.11 createRenderState() extractRenderState(entity, state, ...) submit(state, stack, collector, camera) copy first submit from snapshot later
Live block entitymutable connections, power and facing in the client world
extractRenderStatereads the entity during Minecraft’s extraction phase
SnapshotCableBlockEntityRenderState owns copied values
submitcalculates endpoints without touching the entity
Render queuegeometry is collected, sorted and drawn later
Captured valueHow it is capturedWhy it matters
Connectionsentity.getConnections()The submitted work cannot observe the list changing halfway through a frame. getConnections() already returns an immutable List.copyOf, so the render state stores that snapshot directly instead of copying it a second time per block entity per frame.
PowerCopied as an intCaptured but deliberately unused: power-based cable colour is a separate change, held back for render-cost headroom on slower machines. Note it is not currently a usable signal for connectors either — RedstoneWireBlockEntity.getSignal() returns 0 and RedstoneConnectorBlockEntity does not override it, so a connector’s captured power is always zero.
FacingCopied from the immutable BlockStateInput/output renderers can place their antenna endpoint on the captured side.
C# lens: treat the render state like a small immutable DTO copied from a live domain object. extractRenderState maps entity → DTO; submit maps DTO → render commands. This is similar to preparing a render snapshot before another phase consumes it.

The connector renderer also keeps its position comparison, so a connector-to-connector cable is submitted by only one endpoint instead of being drawn twice. See the connector, input, and output file cards.

2 · What the new render pipeline is

A RenderPipeline is the GPU-facing contract for a kind of drawing. It specifies which shaders run, what every vertex contains, which primitive topology joins those vertices, what samplers are available, and fixed state such as face culling. It does not contain this mod’s individual cable vertices.

Cable renderer — calculates the cable’s four-sided shape and asks to submit custom geometry.
SubmitNodeCollector — records the geometry-producing callback for later rendering and ordering.
RenderType / RenderSetup — pairs the pipeline with runtime setup such as the lightmap.
RenderPipeline — declares shaders, vertex layout, quads, sampler and culling rules used by the GPU.
Cable pipeline settingMeaningC# / graphics analogy
rendertype_leash shadersMinecraft shader programs transform and color cable vertices.Vertex shader + pixel shader.
POSITION_COLOR_LIGHTMAPEach vertex supplies position, color and packed light—nothing else.Vertex declaration/input layout.

withCull(false)Both sides remain visible, useful for thin geometry.Rasterizer cull mode disabled.

One subtle detail: the render-state snapshot currently captures power, and CableRenderer.renderCable(...) receives it, but the emitted cable color remains a fixed dark red. That is preserved behavior, not automatic power-based brightness.

C# lens: the pipeline is closest to a graphics Pipeline State Object, while SubmitNodeCollector behaves like a command-buffer builder. See CableRenderer’s file card.

3 · How BLOCKS.registerBlock and ::new work

The important point is that registration stores a factory now and constructs the block later, during NeoForge’s registry lifecycle.

Java constructor reference

RedstoneConnectorBlock::new

The compiler sees that registerBlock needs a function taking Properties and returning a block. It therefore binds the matching constructor.

Exactly equivalent lambda

properties -> new RedstoneConnectorBlock(properties) // C# spelling: properties => new RedstoneConnectorBlock(properties)

::new is concise Java syntax for passing a constructor as a callable value. It does not call the constructor at this line.

Declarationstore name, constructor function and property customizer
Registry eventNeoForge decides it is time to create blocks
Fresh propertiesProperties.of(), then map color/no-occlusion lambda
Assign IDredstone_wire:redstone_connector is set on properties
Call constructorfactory returns the block; DeferredBlock becomes its handle

The third argument, properties -> properties.mapColor(...).noOcclusion(), is a UnaryOperator<Properties>: it receives the fresh property object, configures it, and returns it. The helper then calls setId before invoking RedstoneConnectorBlock::new. That ordering fixes the startup error Block id not set.

C# lens: DeferredBlock<T> resembles a typed registration handle or Lazy<T>. Use .get() only after the registry has reached the appropriate lifecycle phase. See ModBlocks’ file card.

5 · A Pose is a coordinate transformation snapshot

Here “pose” does not mean a Steve animation. A PoseStack is a push/pop stack of coordinate transformations. Its current top element, PoseStack.Pose, contains the transform needed to move local model coordinates into the current render space, plus the related normal transform used for lighting.

Local cable vertexfor example (0.5, 0.6, 0.5) inside one block
Current Posetranslation, rotation and scale accumulated on the stack
addVertex(pose,…)applies that transformation while writing the vertex
Render-space vertexends up at the correct block/camera-relative location
Matrix4f matrix = poseStack.last().pose(); consumer.addVertex( matrix, x, y, z);
→
PoseStack.Pose pose = poseStack.last(); consumer.addVertex( pose, x, y, z);

C# lens: think System.Numerics.Matrix4x4 or Unity’s local-to-world matrix, with a stack for nested transforms. The new API passes the complete current transform object instead of extracting only its raw 4×4 position matrix.

6 · Why the GameTest coordinates changed

These numbers are fixture-local coordinates, not permanent world coordinates. During this project’s migration, runtime failures and inspection of the unchanged NBT fixtures showed that the local reference frame had moved up by one block.

OLD LOCAL FRAME Y=2 lever / lamp Y=1 first template layer Y=0 controller/origin layer controller counted by helper
−1 Y
NEW LOCAL FRAME Y=1 lever / lamp Y=0 first template layer controller is outside helper-relative template space

No fixture blocks were physically lowered. The same NBT structure is addressed from a different local origin—like changing a model’s pivot and then updating all local coordinates. GameTestHelper.absolutePos(relativePos) still converts those local positions into the actual rotated world positions.

C# lens: imagine changing a Unity prefab’s local origin from a helper object below the mesh to the mesh’s first voxel. The world can look identical while every stored local Y value changes by -1.

7 · Why tests have to be registered now

Documented fact Since Minecraft 1.21.5, the old @GameTest/@GameTestHolder discovery was replaced by registry- and data-driven GameTests. A Java function is registered as a namespaced Consumer<GameTestHelper>, and a test-instance JSON describes how that function becomes a runnable scenario.

Java methodthe assertions and actions
Function registry IDa stable name for that callable
Test-instance JSONselects function, structure, environment and timeout
NBT structurethe physical test fixture
Runnerloads the data, places the fixture and invokes the function

Likely design benefits Mojang’s API establishes the mechanism, but does not state every design motivation. Reasonable benefits are deterministic registry-time discovery instead of reflection scanning; stable resource IDs; datapack validation; the ability to pair behavior with different structures, rotations or environments; and a clean separation between executable Java and scenario configuration.

C# lens: the registry is a namespaced dictionary of Action<GameTestHelper>. Each JSON file is a test-case record that names one action and supplies its fixture/configuration.

8 · onRemove moved to the block entity lifecycle

The cleanup was not deleted without replacement. It moved from the shared block class to RedstoneWireBlockEntity.preRemoveSideEffects, a hook Minecraft invokes immediately before removing that particular block entity.

1 · A connector is broken

The server replaces its block state with air. Because the block type changed and the old state owned a block entity, removal begins.

2 · Minecraft finds the old block entity

LevelChunk.setBlockState obtains it while it still exists at the old position.

3 · preRemoveSideEffects runs

The wire block entity copies its connection list and removes both ends of every connection. The surviving neighbors are marked changed and synchronized.

4 · Minecraft removes the old block entity

Only after the hook returns is the broken endpoint deleted from the chunk.

Why this is safer: cleanup now lives beside the mutable connection data it owns. Ordinary POWER/FACING state updates keep the same block entity and therefore do not accidentally disconnect cables; replacing the block with air does.

The newly added GameTest creates two connectors, links them bidirectionally, breaks one through GameTestHelper.destroyBlock, and verifies that the survivor’s reverse reference is empty. It exercises the real server removal path rather than calling the cleanup method directly. See the test file card.

9 · What the newly added files do

Client item lookup

registered item ID redstone_wire:redstone_connector ↓ assets/redstone_wire/items/ redstone_connector.json (selection / decision layer) ↓ assets/redstone_wire/models/item/ redstone_connector.json (existing geometry/model layer) ↓ block model + textures

The three new assets/redstone_wire/items/*.json files are not duplicate models. They are the modern top-level item definitions that select the existing models for inventory, GUI and hand rendering. They are client resources and do not affect placed-block behavior.

GameTest lookup

test-instance resource ID ↓ data/redstone_wire/test_instance/*.json ├─ function ID ├─ structure ID ├─ environment └─ max_ticks ↓ registered Java function + NBT fixture

The test-instance files are data records that compose runnable tests. Registration names the Java callable; JSON supplies the scenario; NBT supplies blocks. The new removal test deliberately reuses the colored-grid NBT as a bounded sandbox and replaces two cells in Java, avoiding another opaque binary fixture.

src/main/java/at/osa/redstonewire/renderer/CableRenderer.javaModifiedRendering

What changed

  • Added shared CableBlockEntityRenderState.
  • Created named pipeline redstone_wire:pipeline/cable.
  • Selected leash shaders, light-map sampler, no culling, and position/color/light-map vertices.
  • Changed TRIANGLES to QUADS.
  • Uses submitCustomGeometry and PoseStack.Pose.
  • Removed old UV, overlay, normal, and explicit triangle vertices.

Why

Minecraft 1.21.9 introduced the pipeline-oriented rendering architecture used by 1.21.11. The vertex writer must exactly match the declared pipeline format and primitive mode.

What it does

Submits each curved cable segment as six four-vertex faces with color and lighting. Culling is disabled so thin cable faces remain visible from either side.

Behavior note: power is retained in the render state and method signature, but cable color is still the fixed dark red used by the existing implementation. The pipeline and geometry deep dive traces the complete stack.

What I would do next

  1. Reload the Gradle project in IntelliJ. The compiler is using 1.21.11, but the editor index previously retained pieces of the 1.21.1 model.
  2. Run a visual cable test — release blocker. Place connector/input/output blocks, link them with redstone, rotate them, and inspect cables from all sides, including while breaking a linked block. Pipeline registration is proven; appearance is not, and the geometry and overlay state both changed.
  3. Test an existing 1.21.1 world copy. The new GameTest proves fresh connected blocks clean up when broken; a copied old world is still needed to prove that previously saved relative connection lists migrate correctly. Never use the only copy of a real world for first migration testing.
  4. Release version: bumped to 1.0.9. 1.0.8 shipped four months ago and its tag already exists on origin. Because release.yml skips when gh release view finds the tag, leaving the version at 1.0.8 would have made the release job pass while publishing nothing.
  5. Review and commit. A post-review pass removed a redundant per-frame list copy in all three renderers, stripped a UTF-8 BOM from one test-instance JSON, documented the NBT fixture shared between StructureTests and the removal test, and noted why the datagen run is client-only. Tests were re-run green after those edits.
